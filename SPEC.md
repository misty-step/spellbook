# Spellbook specification

Spellbook is Misty Step's harness-neutral engineering method for humans and coding agents, paired with a public handbook and skill-finder site. One canonical content tree in open Agent Skills format serves every supported harness through universal instructions and thin native adapters, while a small always-on core stands alone for small work and routes nontrivial work to one self-contained mode page and on-demand task skills.

Maintained executable agent guidance, skills and harness primitives belong to Spellbook.
Supercortex is the primary context system for agents. Its authorized collections hold
curated context and point to authoritative projects and source archives. The owner's
designation routes agent-intended material, including personal reflections, to its
authorized Supercortex destination. Daybook retains legacy personal records. Portable procedures discover authorized
destinations from local context. Public packages contain no private source material.

Private fleet runtime setup, credentials, host automation and operator scheduling belong outside Spellbook in `misty-step/workstation`, never copied into the public method.

Spellbook was published as Mistystack until the November 2026 rename; `github.com/misty-step/mistystack` redirects to `github.com/misty-step/spellbook`. Stable identifiers outlive the brand: the `misty` skill, `misty-check.mjs` with its flags and `.misty-check.allow`, the `mistystack@mistystack` Claude plugin and marketplace name, the `mistystack-site` worker serving `stack.mistystep.io`, and retired-route redirects. Renaming any of them requires a planned consumer migration, never a silent cutover.

## Terms

- **Specification (`SPEC.md`):** a program's single, implementation-free, present-tense target state owning purpose, domain terms, invariants and observable user capabilities.
- **Homeostasis:** the state where the live running application and `SPEC.md` agree with zero drift, removing the need to materialize a specification into ticket backlogs.
- **Content tree:** the canonical Agent Skills package (`SKILL.md` entry points with supporting files beside each procedure).
- **Universal install:** installing the shared content tree in a harness's Agent Skills directory and placing the core in its always-on instruction file so Cursor, Prime Agent, OpenCode, Gemini CLI and any compatible runtime share one method without a dedicated plugin.
- **Native adapter:** thin repository-owned integration for Claude Code, Codex, pi or Antigravity exposing that same tree and core through the harness's own lifecycle without a custom installer or a second copy of the method.
- **Core rule:** the always-applied entry guardrails and routing (`<= 20` lines).
- **Mode:** `misty`, one self-contained page holding the work loop, ownership, autonomy, delegation, reporting and routes to every task skill, with no base document beneath it.
- **Principle:** an engineering taste heuristic consulted on demand when its trigger matches, never cited as a blanket bureaucratic rule.
- **Conformance:** the finished-deliverable contract of all twelve Foundation articles, separate from the audit procedure.
- **Skill:** a focused procedure directory with a `SKILL.md` entry point and optional supporting files; references resolve within the shared tree while native adapters handle host loading mechanics.
- **Vendored skill:** an upstream skill retained byte-for-byte under a hash-verified lock so local adaptations live in companion shaping facts rather than hand edits to upstream prose.
- **Recompile review:** the monthly desk review, and the rebuild round that a model jump, a spec amendment or structural friction triggers, considering a blank-sheet rebuild from `SPEC.md` (explicitly choosing whether to keep or regenerate UI craft in `DESIGN.md`, and protecting live user data at cutover). Keeping the current system is a valid conclusion.
- **Exemplar:** a person, codebase, piece of writing or product whose perspective Spellbook deliberately channels ([Exemplars](docs/exemplars.md)).
- **Rigor role:** `rigor-light`, `rigor-standard` or `rigor-critical`, classifying changed-path risk independently of any specific model; model and reasoning assignments live solely in harness-native configuration.
- **Provisioning:** choosing an agent's harness, model tier (frontier or workhorse) and effort from its role and work, with each vendor's models run in that vendor's own harness, from the dated routing reference (`skills/misty/routing.md`); live quota and accounts stay outside Spellbook.
- **Task agent:** an independent worker briefed with outcome, terms, raw material, Oracle, owned scope, preserved behavior, rigor and return expectations.
- **Oracle:** a check outside the agent that can disprove completion, stated as a concrete command or real user path.
- **Local development environment:** the environment where the agent executes; each harness note owns its environment constraints.
- **Slice worker:** one isolated machine started from a clean, credential-free toolchain snapshot, reused across a slice's builds, suites and browser checks, stopped while idle and deleted once its evidence is collected.
- **Verified cursor (`verified`):** the fast-forward-only Git branch (`refs/heads/verified`, falling back to the default branch where absent) marking the latest trunk revision proven across its affected surfaces, from which new slices branch.
- **Surface closure:** a repository's complete mapping of tracked files to `non-exec`, named runtime `surfaces` or `shared` (all surfaces), failing closed to every surface on unmapped files so unaffected edits skip runtime replay cleanly.
- **Check budget:** a repository's self-enforced wall-clock limit on `./scripts/check` (`<= 120s` for `fast`; `<= 300s` per surface or shard for `verify`), failing `check_budget_exceeded` until bloated checks are checkpointed, sharded or pruned.
- **Proof receipt:** a content-addressed verification record binding a surface, git-blob Merkle hashes of its surface closure and shared core, runner/snapshot identity, command digest and exit status, trusted for release only when minted by a clean-checkout non-author runner.
- **Coordinator role:** Chief of Staff, project owner, understanding lane or task agent, held only when the user invokes `coordinator` or a parent's launch brief assigns it; hc labels (`misty.role`, `misty.project`) carry logical ownership while native hc parentage records only the launcher.
- **Watchdog:** the active supervisor that periodically compares observed agent work against its brief, steers drift and recovers stalls until acceptance and worker cleanup finish, with no wall-clock deadline on completion.
- **Release gate:** the pre-publication and pre-deployment gate pinning one candidate revision so newer trunk landings wait for the next train, consuming valid clean-runner proof receipts or running fast checks directly alongside one critical-correctness/security assessment, then advancing `verified` (where no sweep daemon runs) and proving live release identity and a critical user journey.
- **Workstation plugin:** the private `misty-step/workstation` plugin owning host runtime setup, credentials and fleet bots; it consumes Spellbook without duplicating it.

## Invariants

1. **Small, always-on core.** The core rule remains at most 20 lines (including frontmatter) and loads automatically in every enabled session; detailed procedures load only on demand.
2. **Skill provenance.** Misty-authored skills use a directory-matching `name`, trigger-first `description`, observed-failure `prevents` evidence, `owner`, quoted ISO `sunset` review date and short `source` identity backed by full directory records in [Attribution](ATTRIBUTION.md#skill-provenance). Vendored upstream skills keep upstream metadata unchanged under registered hash locks (`vendor/`), retain required notices and are regenerated only from pinned upstream revisions.
3. **One page, no layers.** The mode page states the method directly with no base rule document beneath it; method edits update `misty` or a task skill rather than layering overrides.
4. **Harness-neutral method.** One content tree defines the method without naming host-specific tools, private endpoints or model rosters; native adapters and harness notes carry runtime-specific mechanics.
5. **One home per fact.** Domain terms, invariants and observable product capabilities have one authoritative home in `SPEC.md`; visual aesthetic lives separately in `DESIGN.md` for UI projects; architecture, stack choices and historical trade-offs live in [decision records](docs/decisions/index.md); cutovers migrate callers and remove retired homes.
6. **Owned boundary.** Verification and setup operate strictly in isolated state and never overwrite live operator profiles, foreign plugins, credentials or runtime configuration.

## Method

### Always-on core and one-page mode

- Every enabled session loads the concise core automatically (without requiring the user to invoke a skill), enabling small tasks inline (`name intent, finish the work, inspect real running behavior, keep code simple`) and routing nontrivial work to `misty`.
- `misty` equips any capable agent with local Misty Step rules the codebase alone cannot establish:
  - **Work loop:** inspect real sources before summaries; answer empirical questions by running them; bring unsettled product intent to the owner through shaping; name an outside falsifiable check before designing; build minimal complete slices (reshaping structurally when needed); cut accumulated complexity from the first draft before proof; prove on the built running product; deliver and report honestly.
  - **Ownership and autonomy:** repositories owned by Misty Step are freely shaped (merging duplication, fixing adjacent defects, deleting dead code); foreign repositories receive minimal targeted changes. Routine reversible work, slice lifecycle, merging self-proved PRs and native pipeline deploys require no confirmation, while destructive data/resource deletion, shared force-pushes, external outreach, non-pipeline deploys and mandatory team tooling changes wait for explicit owner approval.
  - **Delegation and briefing:** work stays inline by default and delegates only for parallel disjoint slices, bulk research, cross-family second opinions or open-ended supervision, using the brief contract (`Outcome and why`, `Terms`, `Raw material`, `Oracle`, `Scope and keep`, `Effort`, `Return`). Model selection lives in native configuration selected via rigor role (`rigor-critical` never weaker than the dispatching session).
  - **Reporting:** outcome first, claims separated as measured vs inferred vs guessed, explicit gaps left uncovered, owner-behalf decisions stated, and `merged`, `released`, `artifact verified` and `live behavior proven` never conflated.

### Install, setup and verification gate

- `daily-retro`, `setup-mistystack`, `recompile` and `coordinator` remain excluded from automatic model discovery (`disable-model-invocation`) while remaining directly readable at their installed entrypoints.
- Explicitly invoking `setup-mistystack` installs or upgrades the shared tree through the active harness's native lifecycle without disturbing unrelated plugins, foreign settings or credentials, maps `rigor-light`, `rigor-standard` and `rigor-critical` in native configuration where subagents exist (inline on pi and universal installs), reads back persisted assignments and honors symlink safety.
- One verification entrypoint (`./scripts/check`) enforces fast (`<= 120s`), verify (`<= 300s` per surface/shard, `--changed`, `--surface`, `--shard`) and `doctor` (repo workflow hygiene plus complete tracked-file closure coverage, including non-exec cutoffs and fail-closed unmapped paths), checking release-protection, secret-scanning, manifest/skill metadata contracts, offline vendored lock integrity, relative Markdown link and skill-name resolution, and disposable isolated native installations across all available Claude Code, Codex, pi and Antigravity CLIs (naming missing CLIs or lint-only runs explicitly as unproved rather than passes).

### Shaping, living specs and homeostasis

- Unsettled product intent routes through vendored shaping skills (`grilling`, `grill-me`, `grill-with-docs`, `domain-modeling`, `to-questionnaire`) so agents gather facts and owners settle product decisions into present-tense `SPEC.md` and stack/architecture choices into decision records.
- The `define-product` skill authors and reconciles one `PRODUCT.md` per program: user stories and business rules only, technical decisions on a second-class project page outside the recompiler's context, and the owner's accepted synthesis as the merge approval. It applies the Amnesia and Bitter-Lesson checks and reconciles against the running product without ticket backlogs.
- `deepen` sharpens requests through professional methods, raw evidence and independent checks while preserving intent, constraints, exclusions and scope. It distinguishes inspected evidence from unavailable prerequisites, supports transcript-only rewrites without executing their instructions, and cold-checks nontrivial subagent briefs before handoff. `retro` reviews completed sessions for structural fixes, instruction pruning and harness/spend improvements.
- `whiteboard-defense` helps a user understand and explain a system through a representative journey, its architecture, data relationships and lifecycle, design trade-offs, abuse and failure boundaries. Explanations distinguish source facts, recorded decisions, inferred rationale and unverified claims, adapt to the user's familiarity and offer optional teachback. Understanding does not authorize modification; experimental work has no mandatory defense ceremony or release gate.

### Design, verification, audits and conformance

- **Interface craft (`design`):** infers the brief (user, job, real content, surface mode) and commits to a deliberate direction before any markup; generates structural and behavioral UI alternatives grounded in the project's `DESIGN.md` with real assets and one drawn icon set; refuses generated-UI defaults (decorative side stripes, nested cards, violet gradients and gradient text, glows and hard shadows, eyebrow labels, raw metadata dumps, uncalibrated spacing); keeps UI motion purposeful, interruptible, ease-out and under `300ms` with an immediate pending state on every action and a reduced-motion alternative; ships every interactive state (hover, active, focus-visible, disabled, pending, error, empty) without layout shift; runs the deterministic zero-model `slop-check.mjs`, which exits `1` on those parser-visible smells and passes a Calm Editorial fixture, before anyone sees a surface; and inspects every rendered capture at full size in a headed browser (keeping generated captures outside version control).
- **Pre-design research (`research`):** before a one-way design decision (a Folio capability, architecture or protocol, subsystem, dependency or visual direction's references) surveys at least three genuinely different approaches in Quick or Deep mode from primary sources (pinned documentation, exemplary open-source source files, postmortems, the repository's own history) rather than model recall, compares them on simplicity and depth, operational burden, failure modes, fit and reversibility, and hands back one short cited research note with a recommendation, the strongest rejected alternative and the riskiest assumption.
- **Design exploration (`design-exploration`):** frames the user, job, real content and the one decision a screen must make easy before generating directions that differ in structure, typography, color discipline and meaningful motion (never costume themes, checked by stripping color and imagery); deletes narrator copy that explains what the interface already shows in favor of affordance, real sample data and one-to-three-word labels; passes approved marks, diagrams and tokens downstream as checked-in files with checksums instead of prose descriptions; renders every candidate in a headed browser at `1440x900` and `390x844`, light and dark, runs `slop-check`, and has a cross-family Verifier grade restraint, copy economy, typography, motion, real-data fidelity and distinctness before the decision-maker sees it; runs every UI or design pass as a Design Arena of three `model+pack` configurations shuffled into numbered blind slots by `arena.mjs`, records the owner's blind pick, ranking and reason in a durable append-only ledger before the key is revealed, and tallies wins per arm and per part to route future passes, graduate loss reasons into taste invariants or checks, and nominate losing packs for ablation; and briefs models with the why, a few taste invariants and real fixtures rather than CSS checklists.
- **Presentation (`present`):** hands finished multi-step or long-running work back as a reader-first catch-up instead of a wall of text: it picks the lowest medium that carries the meaning (three lines, an inline visual, or an interactive HTML briefing), delivers catch-ups, night-shift summaries and release briefings as self-contained interactive HTML artifacts rather than narrated slideshow videos (real data visualizations, embedded playable video walkthroughs and before/after screenshots as evidence, calm editorial typography with light and dark parity, no external dependencies, and safe on an opaque origin), frames the catch-up in five beats (Look at this, What differs, Pay attention to, Why, Needs you — always answered, even with "Nothing needed"), draws Execution Route Maps of the rules, skills and tools a run actually took when explaining agent behavior, and builds every visual only from evidence that actually ran.
- **Two-axis verification (`verify`):** frames verification as one primitive — independent proof on the real running path that the change achieves its stated intent — performed by the Verifier (the current label for that principle), with refactoring, tidying, redesign and recompilation routed to separately scheduled or triggered passes; the Verifier, from a different model family, states the intent, a failure model proportional to the system's real operating contract, and the pass number before reviewing; proves the change on the real running path (Axis 1, blocking only on unmet acceptance criteria, in-model regressions, security, secret, data or isolation leaks, or missing or dishonest proof, each with a reproduction); grades the diff deeper, neutral or shallower and names defensive over-engineering, forwarding layers, speculative shims and tautological tests (Axis 2, never blocking alone); caps convergence at two passes so that from pass 3 only a reproduced catastrophe blocks (a real leak, loss or corruption of real data, or core user behavior completely broken), while security, secret, data and isolation leaks block at every pass; and opens every verdict with exactly `VERDICT: PASS`, `VERDICT: PASS_WITH_MINOR_FINDINGS` or `VERDICT: FAIL`, separating Blocking from Follow-up Sparks / Minor findings.
- **Project anatomy (`project-anatomy`):** generates on demand a timestamped, self-contained interactive HTML snapshot of a repository's real anatomy (identity stamp, system map, module depth and state ownership, live routes, endpoints, commands and hooks, Active Folio versus reality, recent evolution) derived from the checked-out revision rather than existing docs, in the `present` briefing format, with an embedded JSON block for diffing against the previous snapshot, archived immutably outside the repository.
- **Observability by default (`foundations`):** every deployed web app, worker or service reports its own failures without the owner asking per project: a truthful health endpoint with release identity, production telemetry, and forwarded browser errors, unhandled rejections and Content Security Policy violations feeding automated triage, preferring a same-origin beacon over a vendor script when the policy allows connections to the same origin only. `misty-check.mjs` reports each gap with a fix in text and `--json` output, stays advisory unless `--strict-observability` is passed, treats an incomplete scan (file cap reached, unreadable directory or file) as a failure under that flag rather than as a clean result, accepts `/healthz` or `/api/health` in both the baseline health check and the observability audit, and honors per-rule `observability:` opt-outs in `.misty-check.allow`.
- **Trace mining (`trace-mining`):** regularly mines raw session transcripts, human corrections, friction logs and agent traces (redacted at the source), clusters recurring rejections, corrections, stalls and hand-rebuilt flows with counts, spread and verbatim evidence, ignores one-off bugs, graduates each high-leverage pattern into the smallest durable artifact (a deterministic check first, then a sharper skill rule with its why, then a pruned workflow) while deleting obsolete scaffolding in the same change, and measures whether the failure stops recurring in later traces.
- **Maintenance loops (`reflect`):** a cold reader runs five loops on a cadence — session reflection with a deletion test for rules and skills (extraction owned by `trace-mining`), a verification health check that keeps only checks that fail on a deliberately broken build, a day-one entropy audit shipped as deletions with migrated callers, learning extraction into atomic active-recall items for the human operator, and harness ablation that runs single-variable control-versus-treatment deltas (omit one skill, drop one rule, swap one design-skill pack or model route) on routine work, judges them blind on outcomes, logs every arm to a durable ledger and deletes or promotes components only on accumulated evidence — each ending in one reviewable change judged by what it removes.
- **Consumer verification (`verification`):** proves running behavior on real user surfaces (success, rejection and recovery) using dedicated QA credentials for signed-in roles or explicit composition checks for internal packages, adding reproducible formal property checks (including broken-variant rejection) where ordering, concurrency or durability matter. Checks jump to decision points via deterministic state fixtures after one cold-onboarding smoke journey, prove parameter combinations at narrow state boundaries with one representative on the full surface, assert observable behavior rather than source-text snapshots or generated docs, and stay inside zero-sum `./scripts/check` budgets (`<= 120s` `fast`, `<= 300s` per `verify` surface/shard) under fail-closed surface closures.
- **Specialist audits (`test-audit`, `security-audit`, `foundation`):** prunes noisy tests while preserving independent consumer contracts; performs focused vulnerability audits (reading full pinned workflows upstream only when commissioned); and evaluates all twelve Constitution articles against [Conformance](skills/foundation/checklist.md#conformance), reconciling findings directly or marking owner-blocked items unverified.

### Isolated execution, delivery, release and recompile

- **Coordination (`coordinator`):** an explicitly invoked Chief of Staff delegates all work on a repository to that repository's one long-lived owner, which gives each task or initiative to its own agent and keeps one understanding lane that keeps `SPEC.md`, `ARCHITECTURE.md` and decision records true and teaches the user. Each project has one Herdr space named for the project, with an Ownership tab for its owner and an Understanding tab for its lane; every agent carries role and project labels, so a fresh Chief finds the owners instead of relaunching them, and agents are messaged only while they are live.
- **Execution and supervision (`boat-workers`, `watchdog`):** each slice reuses one credential-free toolchain-snapshot worker (stopped while idle, deleted after exporting artifacts and evidence, reserving fresh egress-blocked machines for untrusted code) supervised periodically without arbitrary wall-clock caps until acceptance and cleanup finish; clean non-author runners mint release-trusted Merkle proof receipts and run parallel shards or bisection checks across independent workers.
- **Delivery and release (`ship-loop`, `merge-risk`, `resolve-merge-conflicts`, `release-watch`):** author-proved slices branch from `origin/verified` (falling back to default branch), pass `./scripts/check fast`, affected `./scripts/check verify --changed` and real-path proof with consumer rationale, reconciled `SPEC.md` section, rigor tier, observed proof, uncovered gaps and category-level Merge Danger verdicts, then land directly without PR CI queues or review bots (either via author squash-merge or pre-reviewed direct push-to-main). Coalesced single-flight sweeps advance `refs/heads/verified` with single-retry flake defect tracking and parallel first-parent bisection + auto-revert (capped at two reverts before hold). Release trains pin one candidate revision without resetting on subsequent trunk commits, consume clean-runner Merkle proof receipts or run fast checks directly alongside one critical-correctness/security assessment, deploy the verified artifact (`prepare → verify → publish → deploy`), advance `refs/heads/verified` where no sweep daemon runs, confirm live serving identity plus a critical journey, and recover safely on failure.
- **Bake-off (`bakeoff`):** an exploration (a design first, an implementation when the shape is open) sends one outcome brief to every Frontier model on its own vendor harness; outputs are shuffled into a numbered blind gallery whose pages show their number and non-identifying metadata, the owner marks likes and dislikes by number before the key is joined, the reveal adds model, harness and effort to each page, and the verdicts land in Supercortex `taste/bakeoffs.md` with one dated observed line in the routing reference.
- **Recompile (`recompile`):** reviews active programs monthly and runs a rebuild round when a model jump, a spec amendment or structural friction triggers it, giving rebuild seats only `SPEC.md`, a kept `DESIGN.md`, a runtime card and a frozen acceptance list; it designs the simplest blank-sheet system from `SPEC.md` before comparing against legacy code, grades every rebuild and live production with one cross-family grader set (runs on the real runtime, conforms, no critical failure, blind quality), turns spec gaps into `SPEC.md` amendments, choosing explicitly whether to retain or regenerate `DESIGN.md`, and gating stateful cutovers on dry-run, unsafe-conversion refusal and rehearsed rollback over realistic user data.

## Public site

### Understand and adopt

- A visitor can understand what Spellbook is, which observed failures it addresses, how `core → misty → relevant method → outside proof` fits together, and how native adapters connect to that same tree without prior repository knowledge.
- The visitor can choose a destination harness and reach its canonical install, refresh, core-loading, rigor and proof instructions; commands come strictly from that harness's maintained reference.
- Integration status distinguishes an available native adapter, a universal-install runtime brief, existing private consumption and missing public setup/loading evidence instead of inventing commands or borrowing another harness's pass.

### Read and find the method

- Guide, Library and Evals are primary reading destinations; Foundation, Decisions, the Specification, Exemplars, Attribution, Changelog and source links remain reachable. Retired `/domain/`, `/stories/` and `/library/skills/to-spec/` / `/library/skills/to-tickets/` URLs redirect cleanly to `/spec/` and `/library/skills/define-product/`, as does `/library/skills/spec/`.
- The library exposes the canonical core, mode and every task skill, including explicit-only skills and supporting documents. Each skill displays its exact installed name and trigger; Misty-authored skills also display prevented failure, owner, provenance and review/sunset date; vendored skills disclose upstream provenance from the lock without invented Misty metadata; supporting documents disclose inherited provenance.
- Each bundled deterministic script (`misty-check.mjs`, `slop-check.mjs`, `arena.mjs`, `extract_conflict_context.py`) has a tool page linked from its skill and the method navigation, showing usage, live build-time output against real inputs where the script has a deterministic one (the repository for `misty-check`, the slop and Calm Editorial fixtures for `slop-check`) and its full source.
- Every page identifies its source path and revision; headings and Foundation articles have shareable anchors (including numeric Foundation aliases); historical ADR references to retired files resolve via explicit archive links; decision status badges display plain text.
- Keyword search finds canonical documents and headings by name, phrase and prevented failure with content-type filters, shareable queries, empty/error states and accessible browse fallback when JavaScript is unavailable.
- Visitors can describe arbitrary tasks at the semantic skill finder and receive every scored preferred-set skill ranked by closeness, disclosing source pack, pin, description, invocation/install command and upstream link alongside served model, known cost, incomplete-scoring status and explicit failure states without fabricated scores.
- Mobile layouts keep navigation, titles, metadata, tables and code readable without horizontal page scroll or hover-only controls; keyboard focus and heading navigation stay operable; light and dark themes follow system preference with user toggle, readable without JavaScript or WebGL under reduced motion.

### Trust content and evidence

- Pages, counts, links, raw source projections and search indexes derive from a single checked-out source revision; publication fails hard on unresolved metadata, broken internal links, missing anchors or duplicate routes rather than shipping a partial library.
- Each evaluation reports task count, arm denominators, method, harness/model, revision limits, measurements, limitations and honest artifact visibility together so new rounds become discoverable automatically.

### Review and operate

- Review previews identify their reviewed commit, link affected pages and carry `noindex` without exposing deploy credentials to untrusted code.
- Production releases expose their serving content revision, promote tested artifacts safely, return real `404` status with search/library recovery on unknown routes, report browser errors, unhandled rejections, Content Security Policy violations and Worker faults to production logs with the release identity, protect query/private text from telemetry, and keep telemetry non-blocking and evidence-backed under the [Foundation checklist](skills/foundation/checklist.md).

## Portable friction capture

At one guarded bounded-work completion per session (and independent native subagent
completion where available), privately ask whether the system annoyed or hindered
the agent. Only a concrete positive answer becomes a size-bounded, secret-screened
observation with stable identity, project/session/harness/model, UTC time, evidence
pointer, impact and business/personal domain. Negative answers write no observation.
Retries do not duplicate an observation. Capture failure never restarts reflection.
Universal completion briefs use the same contract; native hooks are conveniences,
with unsupported lifecycle boundaries explicitly reported. Storage and service
collection authorization belong to the context service, not the portable method.
