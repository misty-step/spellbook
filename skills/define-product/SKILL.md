# Define product

Maintain one present-tense `PRODUCT.md` at the repository root (or per standalone program), paired with `DESIGN.md` as the repository's **Active Folio** — living present-tense truth where git owns history, replacing stale ADR sprawl and ticket backlogs. Code is cheap to regenerate; clear product intent is the durable asset that prevents drift and implementation lock-in. Follow the **3-Layer Intent Stack** inclusion rule: **Universal Baselines** (calm hierarchy, contrast, graceful empty/error states, zero console/CSP errors, real-path verification) apply to every repository, and **Surface-Class Baselines** (Web App, Native/Desktop, CLI/Service, Evidence/Artifact) live in `mistystack` and apply by product kind unless explicitly opted out in Non-Goals — never repeat that generic boilerplate in a repo Folio. Keep `PRODUCT.md` strictly to what is unique to this product: purpose, domain terms, observable user outcomes, business rules, and explicit opt-outs or non-goals — never frameworks, languages, vendors, file paths, or architecture choices. Keep exact headings and structure flexible to fit the project rather than enforcing rigid section templates.

Before scoping or building, push for depth over breadth: start from raw source data and real domain tools over pre-digested tables, set ambitious constraints, falsify assumptions against real telemetry, and name an outside judge to verify the result. Pass every line through two durability tests: if all code vanished, would omitting this line let a clean-room **recompile** break user trust, and would keeping it block a simpler implementation that delivers the same outcome? Shape intent in `PRODUCT.md` first, reconcile the running product directly against it (automatically or on demand) rather than materializing a backlog, and confirm with the user before dropping undocumented live behavior.
